# Security Architecture — Logistics Marketplace

## Overview

This document describes the authentication, authorization, identity propagation, and secret-management strategy used across the Logistics Marketplace ecosystem.

---

## 1. Authentication

### Mechanism

The ecosystem uses **JWT (JSON Web Token)** with OAuth 2.0 / OpenID Connect for user and service authentication.

- **Users (buyer/seller):** authenticated by an external Identity Provider (IdP). The JWT is issued by the IdP and validated by the API Gateway or directly by services.
- **Internal services (M2M):** authenticated through the OAuth 2.0 Client Credentials Flow. Each service has a `client_id` and `client_secret` used to obtain access tokens.

### Token validation

- The **API Gateway** (or BFF) validates the JWT before forwarding requests to microservices.
- Microservices may validate the token again for fine-grained authorization, but MUST NOT call the IdP on every request. JWT signatures should be validated locally with the public key.
- Expired tokens must be rejected with HTTP 401.

### Required JWT claims

| Claim | Type | Description |
|---|---|---|
| `sub` | string | Unique user identifier, mapped to `buyerId` or `sellerId` |
| `client_id` | string | Client application identifier |
| `scope` | string | Authorized scopes, e.g. `shipping:read`, `order:write` |
| `exp` | number | Expiration timestamp |
| `iat` | number | Issued-at timestamp |

## 2. Authorization

### Strategy

Authorization is based on **JWT scopes** at endpoint level and complemented by domain ownership checks.

- Read endpoints: `<domain>:read` scope, e.g. `shipping:read`, `order:read`.
- Write/command endpoints: `<domain>:write` scope.
- Ownership checks: before returning data, the service must verify that the resource belongs to the `buyerId` or `sellerId` represented by the token.

### Authorization example

```csharp
// Controller
[Authorize(Policy = "ShippingWrite")]
[HttpPost("v1/checkout/{checkoutId}/quote")]
public async Task<IActionResult> RequestQuote(...)

// Policy
services.AddAuthorization(options =>
{
    options.AddPolicy("ShippingWrite", policy =>
        policy.RequireClaim("scope", "shipping:write"));
});
```

## 3. Identity Propagation

### Required HTTP headers

Every microservice MUST accept, validate, and propagate the following headers on synchronous calls:

| Header | Requirement | Description |
|---|---|---|
| `x-correlation-id` | Required on every request | UUID used for end-to-end tracking. If missing, the receiving service MUST generate one. |
| `x-client-id` | Required when called by a BFF/channel | Identifies the consuming channel, e.g. `marketplace-web`, `seller-center`. |
| `x-idempotency-key` | Required on command endpoints (POST, PUT) | UUID generated by the client to guarantee idempotency. See [ADR-0005](../adr/0005-idempotency-strategy.md). |
| `Authorization` | Required on authenticated endpoints | Bearer JWT. |

### Propagation across service-to-service HTTP calls

When one microservice calls another over HTTP, it MUST propagate:

- the original `x-correlation-id` — never generate a new one for a propagated call;
- `Authorization` with the caller's M2M token;
- the original `x-client-id`, when present.

```csharp
httpClient.DefaultRequestHeaders.Add("x-correlation-id", correlationId);
httpClient.DefaultRequestHeaders.Add("x-client-id", clientId);
```

### Propagation through Kafka events

`correlationId` MUST be carried in the `correlationId` field of the Kafka envelope for all canonical events and internal saga messages.

```json
{
  "eventId": "uuid",
  "correlationId": "uuid-propagated-from-the-original-request",
  "producer": "order-service",
  "payload": {}
}
```

### End-to-end identity flow

```text
Browser/App
  → BFF (creates x-correlation-id, x-client-id)
    → Checkout Service (propagates headers)
      → Shipping Promise Service (propagates x-correlation-id)
        → Product Catalog, Inventory, Routing, Carrier, Pricing
      ← promise response
    ← quote response
  → Order Service (creates order)
    → Kafka: order.created (correlationId propagated)
      → Shipment Service (correlationId in envelope)
        → Kafka: shipment.created (correlationId propagated)
          → Tracking Service, Notification Service
```

## 4. Secret Management

### Fundamental rule

**Secrets MUST NEVER be committed to the repository**, including:

- database connection strings;
- Kafka bootstrap servers with credentials;
- Redis passwords;
- carrier API keys;
- JWT private keys;
- OAuth client secrets.

### Local development

Use **.NET User Secrets** for local development:

```bash
dotnet user-secrets init
dotnet user-secrets set "Kafka:BootstrapServers" "localhost:9092"
dotnet user-secrets set "ConnectionStrings:Default" "Host=localhost;Database=logistica_envios;Username=logistica;Password=logistica"
```

Credentials present in this repository's `docker-compose.yml` are for local development only and must not be reused in staging or production.

### Staging and production

Recommended options:

- **Azure Key Vault**, with native .NET integration through `Azure.Extensions.AspNetCore.Configuration.Secrets`;
- **HashiCorp Vault** as a cloud-agnostic alternative;
- **environment variables injected by CI/CD** for controlled pipelines.

```csharp
builder.Configuration.AddAzureKeyVault(
    new Uri("https://<vault-name>.vault.azure.net/"),
    new DefaultAzureCredential());
```

### Critical ecosystem secrets

| Secret | Affected services | Recommended mechanism |
|---|---|---|
| Kafka bootstrap servers with credentials | All Kafka-enabled services | Key Vault / environment variable |
| Postgres connection string | Order, Shipment, Tracking, Notification, Audit | Key Vault |
| Redis connection string | Checkout, Shipping Promise | Key Vault |
| OAuth M2M client secret | All services making HTTP calls | Key Vault |
| JWT public key / JWKS URI | All token-validating services | Environment variable; not sensitive |
| Carrier API key | Carrier Service | Key Vault |

## 5. Kafka Event Security

- Kafka events **should not carry sensitive user data** beyond identifiers (`buyerId`, `sellerId`) unless the topic is protected with encryption at rest and in transit.
- Local environments may run Kafka without TLS/SASL.
- Production Kafka MUST use TLS + SASL/SCRAM-SHA-512 with per-service credentials.
- PII such as names or full addresses in Kafka payloads must be evaluated case by case and minimized.
